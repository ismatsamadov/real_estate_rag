# SHA-256 — content hashing for idempotent ingest

**TL;DR.** A cryptographic hash function that turns any string into a
fixed 64-character hex digest. Same input → same output, deterministic.
We use it as a fingerprint for chunk content, so re-ingesting unchanged
text skips the (expensive) embedding step.

## What it is

SHA-256 is one of the SHA-2 family of hash functions, standardized by
NIST in 2001. Given any input — a sentence, a binary file, anything —
it produces a 256-bit (32-byte) digest, displayed as 64 hex characters:

```js
crypto.createHash("sha256").update("hello").digest("hex");
// → "2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824"
```

Three properties that make it useful here:

- **Deterministic** — same input always gives same digest.
- **Avalanche** — changing one character changes the whole digest
  unrecognizably. There's no "almost matches" — either two contents are
  byte-identical or their hashes differ completely.
- **Collision resistant** — finding two different inputs that hash to
  the same digest is computationally infeasible.

The third property is overkill for our use case (we don't need
cryptographic security, just a unique fingerprint), but SHA-256 is the
default everywhere — Node ships it, no dependencies needed.

## Why we use it

The ingest pipeline reads the JSONL corpus and re-chunks each document.
For each chunk:

```js
const content = "...the chunk text...";
const hash = sha256(content);

// Have we seen this exact content for this (doc_id, chunk_index) before?
if (existingHash === hash) {
  skipEmbedding();   // ← saves a Voyage API call (~$0.0001 per chunk)
} else {
  embedAndUpsert();
}
```

Three reasons this matters:

1. **Cost control.** Re-running ingest on an unchanged corpus would
   otherwise re-embed every chunk. With ~850 chunks at Voyage rates that's
   ~$0.50 per redundant run. With content-hash skipping, it's ~$0.
2. **Speed.** Skipping embedding means the no-op re-ingest finishes in
   seconds, not minutes.
3. **Demo iteration.** During development I re-ran ingest dozens of
   times. Content-hash skipping made that workflow free.

## Why not a simpler hash?

A simple checksum (CRC32, MD5) would technically be fast enough. SHA-256
is chosen because:
- It's in Node's standard `crypto` module — zero dependencies
- The hex digest is a clean 64-char string for use as a column value
- Future-proof: if we ever need to use it for content addressing across
  systems, we're not stuck with a weak hash

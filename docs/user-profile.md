# Persistent user-intent profile

## What it is

A **standing summary of who a user is and what they're looking for**,
generated by an LLM from their saved listings, prior questions, and
uploaded documents, then cached in Postgres and injected into the system
prompt **every turn** of every session.

Memory-based RAG (recall top-K prior Q&A by cosine similarity) tells the
LLM what the user *discussed before*. The profile tells it what the user
*wants overall*. The two are complementary — the profile is the synthesis
layer over the raw memory rows.

## Why we built it

Plain RAG-over-history is query-conditional: it only recalls past turns
*semantically similar to the current question*. If the user asks
"recommend something" in a brand-new session with no in-session history,
classic memory recall returns nothing — the new question shares no
vocabulary with prior Q&A.

A profile flips the relationship. The model always knows:

> "This user has saved Knightsbridge 2BR, asked twice in Azerbaijani
>  about St Regis units, uploaded a PASHA Bank Annual Report —
>  likely on a due-diligence track."

…and can answer "recommend something" coherently on turn 1 of a fresh
session.

## How it works

Two-tier context:

### Tier 1 — Structured signals (every turn, deterministic SQL)

Five queries fire in parallel via `Promise.all`:

1. **Profile row**: cached `summary` + `refreshed_at` from `user_profile`.
2. **Favorites** (top 8): joined through `documents` for titles.
3. **Recent topics** (top 8): `metadata->>'question'` from `conversation_memory`.
4. **Uploads** (top 6 unique): `DISTINCT ON (title)` across all sessions.
5. **Counts**: total `memory_n`, `favorite_n`, `upload_n` for staleness checks.

Total wall time ≈ slowest individual query. None of these require an LLM
call — they're free.

### Tier 2 — LLM-synthesized intent summary (cached, refreshed lazily)

After each grounded turn, we trigger `maybeRefreshProfile()`
**fire-and-forget** (the user's response has already streamed). It:

1. Reads the current signal counts.
2. Compares to `basis_*_n` stored on the last summary.
3. If `delta < 3 AND ageMs < 60_000` → throttle, skip.
4. Otherwise builds a compact text input from the signals and calls Claude
   to write a 1–2 sentence "intent profile".
5. Upserts `summary` + new basis counts + `refreshed_at = NOW()`.

The user never waits on this — it runs after the SSE stream closes.

### Injection

`buildUserProfileBlock()` in [`src/prompt.js`](../src/prompt.js) formats
the context like:

```
USER PROFILE (personalization context — proactively reference when relevant;
NOT citable as a factual source):
Intent: User is browsing high-end residential apartments in Baku…
Saved listings (2): Knightsbridge Residence · The Residences at St Regis
Recent topics:
  - "What apartments are available at the St. Regis Baku?"
  - "Knightsbridge-də neçə otaqlı mənzillər var?"
Uploaded docs: PASHA Bank Annual Report 2022 (174p)
```

This block sits **above** the memory block and the question/sources, so
the model frames every answer against the user's standing intent first.

## Key design choices

| Choice | Why |
|---|---|
| Summary stored, signals computed live | Signals are cheap SQL; storing them would create staleness bugs. Summary is the only thing worth caching — it costs an LLM call. |
| Refresh fires **after** the response stream | Zero added latency on the user-facing critical path. |
| Throttle `>= 3` new signals OR `>60s` | Bounds Haiku/Sonnet spend even under heavy interaction. |
| Inject summary as advisory, not citable | Model must still cite `[Sn]` for facts. Profile is for tone/framing/reference. |
| Joined through `sessions.user_id` | Owner check is implicit in the SQL — no extra auth code. |

## Tradeoffs vs alternatives

| Approach | Pro | Con |
|---|---|---|
| Pure RAG-over-memory only | No extra LLM calls; honest "I only know what's relevant" | First-turn fresh sessions feel cold; no synthesis across topics |
| Profile only, no memory | Always-on personalization | Loses precise references to specific past Q+A |
| **Profile + RAG-over-memory** | Synthesis + precision | One extra LLM call per refresh cycle (throttled) |
| Structured slot-filling (preferred_bedrooms, max_price…) | Rigorous, queryable | Brittle; doesn't capture taste, language, depth of interest |

## Privacy

- `DELETE /api/profile` clears the cached summary.
- `DELETE /api/memory` clears memory **and** profile in one call
  (consistency: if memory was the basis, the summary should go with it).
- All reads are scoped to `user_id`; no cross-user leakage by
  construction.

# UUID — Universally Unique Identifier

**TL;DR.** A 128-bit identifier that's globally unique without a central
authority. Used as the primary key for chat sessions because we want the
ID generated on the database (`gen_random_uuid()`), URL-safe, and
unguessable. Format: `xxxxxxxx-xxxx-Mxxx-Nxxx-xxxxxxxxxxxx`.

## What it is

A UUID (Universally Unique Identifier, sometimes called GUID) is a
128-bit number, almost always printed as 32 hex digits in five
hyphen-separated groups:

```
2879c47c-3a9f-47f8-bc8e-4e2983e85f30
```

That `M` position encodes the **version** (we use **version 4** =
random) and `N` encodes the **variant** (the bit pattern that says
"this is an RFC 4122 UUID").

UUIDv4 is generated from cryptographically random bytes. Two UUIDs
generated independently anywhere in the world have a vanishingly small
probability of colliding — astronomically small enough that we treat
collisions as impossible.

## Why we use UUID for sessions, not BIGSERIAL

Both work as primary keys. The tradeoffs:

| | `BIGSERIAL` (auto-increment integer) | UUID |
|---|---|---|
| Size | 8 bytes | 16 bytes |
| Generated by | Database (sequence) | Database, app, or anywhere |
| URL appearance | `?c=42` | `?c=2879c47c-3a9f-47f8-...` |
| Guessable | Trivially — `?c=43` is "the next one" | No |
| Sortable by time | Yes (sequential) | No (random) |
| Multiple writers | Coordination needed | None — independent generation |

For **chat sessions** the URL is in the user's address bar (`?c=...`)
and we don't want users sharing or accidentally browsing to someone
else's session by tweaking the number. UUIDs are unguessable; that
matters even though we already have an auth gate. Defense in depth.

For **chunks and messages** the ID is never in the URL — just a foreign
key inside the database. BIGSERIAL is fine, and 8 bytes saves space
when you have 800k+ rows.

## How Postgres generates them

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;
session_id UUID PRIMARY KEY DEFAULT gen_random_uuid()
```

- `pgcrypto` is a Postgres extension that ships with most distributions
  (Neon includes it).
- `gen_random_uuid()` returns a fresh UUIDv4 on every call. No
  parameters, no coordination, no race conditions.

We don't need to specify a UUID in the INSERT — Postgres generates it
for us, then returns it via `RETURNING session_id`.

## Validating user-supplied UUIDs

The API routes that accept a `sessionId` (e.g. `/api/ask/stream`,
`/api/sessions/[id]`) validate the format with a regex before touching
the database:

```js
const UUID_RE = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i;
```

A malformed value returns **400 Bad Request** instead of going to
Postgres and triggering a 22P02 error. The regex matches both lowercase
and uppercase since RFC 4122 doesn't specify case.
